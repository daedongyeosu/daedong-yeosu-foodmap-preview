# 사장님 입점·꾸미기·배송비 경험 기준

2026-10-17 사용자가 요청한 기준. 기능을 늘리는 것보다 사장님이 기존 자료를 다시 입력하지 않고 시작하는 경험이 우선이다. 이 문서는 구현 상태와 앞으로 할 일을 구분한다.

## 이번 변경과 보존 경계

- 문제: 상점 견본의 가까이보기 버튼은 공간을 강제로 넓혀 좌우로 잘라 보이며 일반적인 사진 확대와 다르다.
- 이번 구현: `store-studio`에서 가까이보기/공간 전체보기 토글을 제거한다. 고객 모드의 공간과 상품사진은 브라우저 기본 두 손가락 확대/축소와 스크롤을 허용한다. 사진 터치→상품 확인→장바구니는 유지한다. 편집 모드 사진/가구 끌기·잠금·되돌리기는 보존한다.
- 변경 금지: 운영 메인, 기존 가게/사진/메뉴/가격/주문·지도 링크, 실제 요율/PG/정산/배차/공유 설정, 이전 고객접수 서버 패치. preview도 사용자 승인 전 병합·배포하지 않는다.
- 검증 한계: 모바일 자동화에서 상점 네 업종의 계산된 터치 허용값과 조상 요소, 버튼 부재, 상품 선택/체험 장바구니, 두 손가락 입력 후 배치 불변을 검사한다. 이 호스트에서는 제한 없는 대조 화면도 실제 배율이 변하지 않아 **실제 손가락 확대 배율은 미검증**이다. 실제 휴대전화 확인이 남는다. 네이티브 확대를 강제 배율 API로 대신한 뒤 성공이라고 보고하지 않는다.

기술 기준: [MDN touch-action](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/touch-action)의 조상 요소까지 포함한 제스처 허용 규칙을 적용한다. viewport에서 확대를 금지하지 않는다.

## 다음 구현1 — 기존 맛지도 가게에서 온라인상점 시작

사용자 경로: 해당 가게카드의 **온라인 상점 등록하기** → 기존 정보·메뉴·음식사진을 채운 기본 표준상점 초안 → 사장님이 가격 확인·설정 → 필요하면 내부/외부 꾸미기 → 확인 후 공개.

- 새로 사진/메뉴를 전부 입력하게 하지 않는다. 기존 공개용 상세/메뉴 API의 확인된 해당 가게 자료를 재사용한다. 다른 가게·잘못 매칭된 메뉴를 끌어오지 않는다. 가격은 경쟁 주문앱에서 추정하거나 가져오지 않고 사장님이 매장 판매가격으로 입력·확인한다.
- 초안 생성은 공개 전환이나 소유권 부여가 아니다. 공개·결제·정산 연결 전 실제 상점주 확인과 기존 자료 이용 권한 확인이 필요하다. 초안부터 모든 개인정보/사업자 서류를 요구하지 않는다.
- 기존 가게 ID와 메뉴/변형의 원본 연결을 보관한다. 온라인상점 ID가 별도로 필요하면 sourceStoreId를 매핑한다. 같은 가게를 다시 눌러 중복 초안을 만들지 않는다. 기존 작성 중인 다른 가게 초안은 확인 없이 덮어쓰지 않는다.
- 기본 상점은 가게명·카테고리·주소·연락처와 원래 메뉴별 사진/설명을 표시한다. 사진이 없는 메뉴는 사진 없음으로 남기며 다른 메뉴 사진을 임의로 대신 붙이지 않는다. 자료가 없거나 오류면 빈 결과를 성공으로 저장하지 않고 재시도/직접 추가를 안내한다.
- 가져온 메뉴를 한 화면에서 나열해 가격만 빠르게 입력/수정한다. 미입력은 **가격 미설정·판매 전**이며0원 판매로 바꾸지 않는다. 판매용 가격이 확정되지 않은 상품은 구매할 수 없다. 문의 상품은 별도 표시한다. 미입력 가격/원문/사진/메뉴 ID를 새로고침 후에도 보존한다.
- 기본 표준상점으로도 시작할 수 있다. 원하면 같은 초안으로 꾸미기에 들어가 내·외부, 간판, 색, 재질, 진열장/사진 배치를 바꾼다. 꾸미기가 상품번호·가격·장바구니/재고를 새로 만들지 않는다. 상품이 많을 때 목록/사진을 나눠 불러오고 먼저 사용 가능한 화면을 보여준다.
- 기준 화면 순서: 가게카드→가져온 메뉴3개 확인→가격3개 입력→기본 진열장→고객 상품 선택→장바구니 합계. 실패/취소/재방문/중복 터치/다른 가게 초안 보호/신규 입점 경로도 검사한다.

## 다음 구현2 — 배송비 부담 비율 막대

배송요금 자체를 사장이0/2,000/3,000원으로 임의로 바꾸는 기능이 아니다. **서버가 확정한 총 서비스 비용을 상점과 고객 중 누가 얼마나 부담할지** 정하는 기능이다.

| 막대 값: 고객 부담률 | 상점 부담률 | 의미 |
| --- | --- | --- |
| 0%: 왼쪽 | 100% | 상점 전액 부담·고객 부담0원 |
| 50%: 가운데 | 50% | 상점과 고객 반반 |
| 100%: 오른쪽＋ | 0% | 고객 전액 부담 |

- 표기는 배송비 조절하기 또는 배송비 부담 나누기로 쉽게 한다. 좌우 끝에 상점 전액/고객 전액을 명확히 쓰고 현재 고객/상점 비율과 각 원화 금액을 같이 보여준다. 키보드/스크린리더가 사용할 수 있는 range와0/50/100 바로 선택을 제공한다.
- 사용자가 지정한 맛지도 이용금액 기준은500원. 기사 수행료와 결제 처리비용까지 누락 없이 회수하는 총요금 산정이 목표다. 막대를 움직여 기사료나 플랫폼 몫이 줄어들게 하지 않는다. 이는 실제 운영 요율 변경 지시나 카드비용 전가의 적법성 확인 완료를 뜻하지 않는다.
- 카드 등 실제 PG 계약 요율/고정비/부가세/환불 기준은 임의로 정하지 않는다. 상품대금까지 결제하면 처리비용 기준이 배송비만은 아닐 수 있고, 결제총액이 달라지면 비용도 달라질 수 있다. 카드 고객에게 가맹점수수료를 별도 전가하는 방식 또는 이름만 배송비로 바꾸는 방식을 승인한 것으로 해석하지 않는다. 실제 적용 전 PG 계약과 관련 규정을 확인하고 적합한 서비스 요금 구조를 확정한다.
- 비용이 확정되지 않았으면 정확한 총액/무조건 무료를 표시하지 않는다. 산정 예시는 예시로 구분한다. 고객에게는 상품금액·고객 부담 배송서비스 요금·최종 합계와 필요한 내역을 투명하게 표시하며 포함된 이용금액을 다시 더하지 않는다.
- 계산 규칙: 확정 총요금B, 고객 부담률p에 대해 고객 부담=원 단위 반올림(B×p/100), 상점 부담=B−고객 부담. 양쪽 합계는 항상B이며 음수/초과/이중 부과가 없어야 한다. 예시B=4,000원이면0/50/100%에서 고객은0/2,000/4,000원이고 상점은4,000/2,000/0원이다. 실제 주문 요금이4,000원이라는 뜻이 아니다.
- 상점 부담액은 고객의 상품대금 할인으로 위장하지 않고 정산에 별도 기록한다. 상품대금보다 지원액이 클 때 숨은 음수 정산을 만들지 않으며 부족액/운영 허용 조건을 먼저 안내한다. 취소·부분환불·여러 가게 묶음 주문에서도 합계를 대조한다.
- 설정은 `deliveryCostSharing: {mode:'ratio', customerPercent:0..100}`처럼 고정 지원액과 구분해 저장한다. 기존1,000/2,000원 지원 초안을 예시 요금으로 나누어 임의의 비율로 바꾸지 않는다. 비율 방식 전환은 사장이 새 설정을 확인한 후 적용하며 서버 견적·주문 스냅샷·상점 정산까지 같은 버전을 사용한다.
- 기본값은 고객100%로 하여 사장이 선택하지 않은 부담을 강제로 부과하지 않는다. 실제 적용 시에는 원 단위 경계(1원/홀수),0/50/100, 저장/복원, 기존 고정액 보존, 실제 총요금 변경/만료, 할인·취소/환불, 원장 대조를 검사한다.

참고: [토스페이먼츠 요금 안내](https://www.tosspayments.com/about/fee), [한국소비자원 가맹점수수료 전가 관련 결정 사례](https://www.kca.go.kr/odr/bj/br/osBjDecisionExamDetW.do?brdId=00000007&dataStts=Y&seq=1001419941). 이 자료가 맛지도의 최종 계약/법률 검토를 대신하지 않는다.
